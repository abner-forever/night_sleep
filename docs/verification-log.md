### 一、改了什么（判定换引擎，不是调阈值）

| 之前 | 现在 |
| --- | --- |
| 四类手写声学特征 + 一组写死的阈值，滑动窗找事件、要求持续 ≥2500 ms | **YAMNet**（AudioSet 521 类）的 `Snoring`(38) / `Speech`(0) 分，按**整段均分**判定 |
| 47 段人工标注上覆盖 **2% / 准确 0% / 鼾声召回 0%** | 同一批数据上零样本 **3/3 命中、0 误报**（桌面 Python 那一轮量的，见 v3.35 §六） |

判定线：**鼾声 0.40 / 人声 0.70**（`YamnetParams`）。依据串换成模型分
（`YAMNet 鼾声分 0.85（整段 8 个窗口均分、最高 0.92，判定线 0.40）· 人声分 0.02`）。
**新判定不产出事件区间**——模型按整段给结论，画一对秒数就是把没量过的东西画出来。

### 四、迁移：旧引擎的判断被作废（**本仓第一条改数据的迁移**）

`app_database.dart` v7 → v8：把 `source='recording' AND analysis_status='analysed'`
的行清回 `pending` 并清空 `auto_analysis`。**动的是机器那一列，用户自己标的 `kind`

### 五、审查发现、我采纳的与没采纳的（记下来免得下次重新想一遍）

对照实现前的一次独立审查：

- **采纳**：均分的盲区必须说出来（见未验证第 3 条），所以依据串里**多摆一个最高分**；
  `AnalysisOutcome` 那个新返回类型砍掉了（界面本来就从库里的行现算「几段有判断」，
  新类型是重复的），改成抛 `ClipModelUnavailable`，**不改任何签名**；
  假打分器必须是顶层函数、不许把数据库圈进闭包（`Isolate.run` 会隐式送走作用域里
  送不出去的东西）；批处理加了一道串行化（撞车时两份 4 MB 模型是新的代价）。
- **没采纳**：把判定改成按**最高分**或按「连续够长的窗口」。那要换一个**没有量过**的
  统计量——上面那些把阈值定到 0.40 的数字全都是拿均分量出来的。改成最高分等于把
  「实测支持的结论」换成「看起来更聪明的猜测」。
- **没采纳**：让迁移保留 `auto_analysis` 旧值只改状态。那样卡片会在重算之前继续显示
  旧引擎的结论，而它与新结论在库里长得一模一样、分不开。

1. **真机上一段真实录音都没有，所以「端侧算出来的分」一个都没量到。**
   `com.example.night_sleep` 已经被卸掉了（手机上只剩 `com.nightsleep.bleprobe`），
   连带上轮那 47 段 WAV 与人工标注的库**一起没了**；`flutter drive` 又会在每次跑完

   合成信号**，只证明「跑得动」，不证明任何正确率。
   **顺带一条更硬的**：本机那份 `.tmp-device/`（47 段 + `labels.txt`）也**已经不在了**，
   所以 v3.35 §六 那次桌面 Python 复算**不可重跑**。那一节留下的数字是唯一的一份。
2. **两个阈值都不是定稿。** 鼾声 0.40 有两组实测撑着（他自己 3 段 0.708–0.850、
   44 段负样本最高 0.305；ESC-50 上 33/40、200 条 0 误报），但**加起来只有 43 条正样本**。
   **人声 0.70 这一档根本没量过**——文档里只量过 0.3 / 0.4 / 0.5（最好的一档是 0.5 的
   80% 召回 / 80% 精确）。0.70 是使用方要求「收得更紧」之后取的，标准是「宁可漏也不误报」。
3. **均分有一个已知盲区，这一版没有绕开它。** 一段 11.8 秒的录音里只有前 3.5 秒是鼾声，
   鼾声那几窗能到 0.9，均分却被摊到 0.3 上下 → 弃权。**这不是新引入的**（旧规则同样在
   整段平均上栽过），而是**换模型之后仍然继承下来的一条**。依据串里摆出最高分就是为了
   让它可见（`均分 0.31、最高 0.91` 一眼看得出「里面有一截很像」）。要真按它判，
   得先重新量一遍按最高分或按窗口连长的效果。
4. **旧规则的时长门槛（2500 ms）没有替代品。** 旧规则靠它挡掉「1.1 秒的拖椅子声」；
   新判定只看整段均分，**一个 1.1 秒的片段只要那一窗的分够高就能拿到标签**。
   这是有意的取舍（那个门槛是照手写特征定的，模型不吃那套），但**没有样本验证过
   新判定在短瞬态上会不会误报**。
5. **iOS / macOS 一个字节都没跑。** Windows 上这两个平台根本构建不了。已知的两个障碍：
   `macos` 的 `libtensorflowlite_c-mac.dylib` 在 `tflite_flutter` 的 podspec 里
   **`s.vendored_libraries` 是注释掉的**，而 Dart 侧按固定路径去
   `Runner.app/Contents/Resources/` 找它；`ios`/`macos` 都还没有 Podfile，
   首次构建要联网解 pod。**这两条不解决，那两个平台上的判定是静默失效的**
   （加载失败 → 抛 `ClipModelUnavailable` → 详情页说「模型没能加载起来」）。
6. **`yamnet.tflite` 的许可证仍未落实**——发布阻塞项（YAMNet 权重与模型文件内嵌元数据
   都是 Apache-2.0，但 MediaPipe 的**文档**没有正面声明这个转换件）。与「助眠音效素材」
   同一类，README 的「未实现」表里已经单列一行。
7. **耗电没有读数。** 只量了耗时与 RSS。一晚 5.3 秒的 CPU 时间摊到整夜可以忽略，
   但这是推算，不是测量。
8. **`Speech`(0) 这一路的分与 `Snoring` 常一起偏高**：v3.35 §六 记过 3 段鼾声的

   有没有把这个影响压住，**没有样本可看**。
9. **界面上「模型分」这个词的使用方反馈没有收到。** 依据串从「低频能量 66% · 谱质心
   391 Hz」换成了「YAMNet 鼾声分 0.85」——**前者他核过，后者他没有**。

### 二、为什么一段都判不出来：是结构，不是阈值差一点

`tool/analyse_clips.dart` 之外另跑了一个一次性诊断（逐窗判、统计过阈值的窗口），读数：

| 量到的东西 | 数 |
| --- | --- |
| 整段短于 `minEventMs`（2500 ms）的段 | **17 / 27** |
| 整段时长中位数 | 约 2.0 秒（最长 8.5 秒，最短 1.0 秒） |
| 过鼾声四条阈值的窗口 | 8 个（散在 5 段里） |
| 过疑似人声四条阈值的窗口 | 18 个（散在 8 段里） |
| 连成够格事件的段 | **0** |

**17 段是决定性的那一行**：一个 1.2 秒的片段里生不出 2500 ms 的事件，无论声学特征多像。
剩下 10 段则是「过线的窗口太散」——153 个窗口里只有 26 个过线，凑不出连续的 2500 ms。

根源是**两组参数各调各的**：切片在跌到 −45 dBFS 后 2 秒就收尾
（`ClipParams.silenceDuration`），一晚的声响被切成 1–3 秒的碎片；而判定的
`minEventMs = 2500` 要求**单段之内**连续 2500 ms。两个数在各自的规格下都有理由
（切片要「一个有声响的时段一段」；2500 ms 是照那段 1.1 秒的拖椅子声定的），
**但从没有人把它们放在一起看过**。详见规格 §七·11。

#### 顺手把「放宽时长门槛能不能救」量了：救不了

### 三、顺带量到的一条正面结论：前台服务整夜有效

v3.19 那次实测的结论是「整夜存活成立，**但录到的是平台交上来的数字静音**」，
v3.26 加了 Android 前台服务之后**「它挡不挡得住那次静音」一直留在未验证里**。
这一晚的数据第一次给出正面证据：

| 量到的东西 | 读数 |
| --- | --- |
| 27 段的响度（整段 RMS） | **−27.8 … −46.0 dBFS**，没有一段是 −160（数字静音） |
| 深夜（应用早已不在前台）的片段 | 05:10、07:33、08:08 都有，**且都是真音频** |
| 读不出来的段 | **0**（47 个文件全部是可解析的 PCM16 WAV） |

**平台静音时交付的是逐样本全零，那既触发不了 −38 dBFS 的切片、也量不出 −30 dBFS 的响度。**
所以「05:10 和 07:33 还录得到真声音」这件事，说明那一夜的麦克风**没有被平台从应用手里拿走**。

**这仍是推断，不是那次 v3.19 判据的复现**：`dumpsys activity services` 的 `isForeground`、

是从产出反推的。**未验证项照旧留在下面。**

### 四、改了三处（都只碰「说出来」，不碰判定规则）

1. **展开区补两句**：弃权写「机器看过这段，没有把握下结论，所以留给你听。」，
   `failed` 写「机器没能分析这段：音频读不出来。它仍然可以回放。」。
   此前这三种情况（弃权 / 读不出来 / 从没分析过）在屏幕上**完全一样**——都是「待标注」，
   展开区一个字不说。这两句**刻意不复用「自动判断依据」那个盒子**（那个盒子摆的是测出来的数）。
2. **「重新分析」跑完报结果**：「看过 N 段，其中 M 段给出了自动判断」；M 为 0 时说
   「没有一段有把握，仍留待标注」；一段都没定案时说「没有可分析的片段」。
   此前它只刷新数据不报结果，而**最常见的结局恰恰是零结论**，于是看起来就是没生效。
3. **`tool/analyse_clips.dart` 表头列名错位**：最后一列标题写「音节」，打的却是

   （`spectralPeakShare`，同为判据）一列，让表里的判据齐了。

### 六、零样本 YAMNet 实测：**换模型这条路的第一道关过了**

使用方问「那你这识别算法有啥用呢……看看有啥通用的开源方案吗」。调研（当晚做完，落成
[鼾声 / 梦话检测：市面做法、开源方案与端侧可行性](superpowers/specs/2026-10-16-snore-detection-approaches-design.md)）
给出的头号候选是 **YAMNet**（AudioSet 训练，521 类里 `Snoring` = index 38 / `/m/01d3sd`，
Apache-2.0）。当晚就在本机拿那 47 段跑了零样本。

**环境**：Windows 11 / Python **3.14.5**（venv）/ **`ai-edge-litert` 2.3.0** /
MediaPipe `yamnet.tflite`（**4,126,810 B**，HTTP 头核对过）。窗口 15600 点（0.975 s）、
步进 7800 点，逐窗取分后**对整段求平均**。

**先核了模型接口**（这一条很重要，它决定「要不要在 Dart 侧自己算 mel」）：

```
INPUT:  waveform_binary  shape=[15600]  dtype=float32
OUTPUT: tower0/network/layer32/final_output  shape=[1, 521]
```

**模型自己在图内算频谱**（RFFT2D + COMPLEX_ABS + LOG），所以喂**原始波形**即可——
调研里从 flatbuffer 解出来的那条结论，在这里被实际加载印证了。

`Snoring` 均分（整段平均）：

| 人标 | 段数 | 最大 / 中位 / 最小 |
| --- | --- | --- |
| **打鼾** | 3 | **0.850 / 0.742 / 0.708** |
| 梦话 | 10 | 0.013 / 0.000 / 0.000 |
| 杂音 | 34 | **0.305** / 0.005 / 0.000 |

| `Snoring` 阈值 | 召回 | 精确 | TP | FP | FN |
| --- | --- | --- | --- | --- | --- |
| 0.3 | 100% | 75% | 3 | 1 | 0 |
| **0.4 – 0.7** | **100%** | **100%** | 3 | **0** | 0 |
| 0.9 | 0% | — | 0 | 0 | 3 |

**正类最小 0.708、负类最大 0.305，中间是一条 2.3 倍宽的空档。**
对照同一批 47 段上现有启发式的 **覆盖 2% / 准确 0% / 鼾声召回 0%**，这是量级上的差别。

**梦话那一路（`Speech`(0) 均分）不干净**：阈值 0.4 时召回 90% / 精确 75%（9 正 3 误 1 漏）。

**判定为「第一道关过了」，理由是**：这三条路里唯一一条「不需要训练、不需要标注、不需要网络」
的路，而这三样正是本仓最缺的。**但它只是一道关，不是结论**——见下面的未验证。

**顺带更正了调研文档里的一条预判**：它写「本机 Python 3.14 跑不了 TFLite，得另建 ≤3.13 环境
或改用 onnxruntime」。实测**不成立**：`ai-edge-litert` 2.3.0（`tflite-runtime` 的官方后继）

「模型只对他这 3 条有效」是这条路最大的风险。所以拿 **ESC-50** 重跑一遍：

### 七、未验证（这一半是重点）

- **零样本 YAMNet 只在桌面 CPU 上跑过，端侧一个字节都没跑。** 这一轮全程是

### 四、改了什么：拆掉「杂音」兜底

原来 `classifyClip` 在「一个够格的窗口都没找到」时返回 `AutoLabel.noise`。拆掉的理由：
**报杂音等于同时断言「不是鼾声」和「不是人声」两个否定结论，而机器认不出鼾声（召回 0%），
没有资格下这个否定结论。** 白天那 81% 的准确率是靠「总是说杂音」买来的（16 段里 15 段
机器只说了杂音，而人标里 14 段确实是杂音），代价是**对着两段真鼾声说「这是杂音」**。

- `classifyClip`：没有事件 → 一律弃权。新增一条不变量用例钉住「**任何**输入都不产出
  `AutoLabel.noise`」。
- `noiseMinDbfs` 保留但改了职责：从「杂音的下限」变成**三道判定通路上游的一道闸**，
  挡数字静音与近乎无声的片段。原来钉它的那条用例**在新代码下不会再变红**（全零输入
  无论门槛多少都弃权），所以换了一条真能钉住它的信号：一段放大 1000 倍就是本文件里
  判得最稳的鼾声、**缩小 1000 倍后只可能被响度闸挡住**。
- `_Detection.windows` / `marginal`（过阈值但余量不够的窗口计数）随之删除——它当初唯一
  的用途就是区分「弃权」与「杂音」。
- `AutoLabel.noise` 枚举值、界面三态、`sound_clip` 卡片那一支**全部保留**：旧记录的
  `auto_analysis` 里还写着它，删掉等于让那些记录读不回来。

使用方说明：**那段 21.6 秒确实是他的鼾声，而这期间风扇一直开着。** 这条把诊断整个改了：

- **风扇的能量是连续的、而且很可能更响**，所以整段平均出来的频谱**被风扇主导**——
  我量到的每一个整段特征都是风扇的值。鼾声是**叠在上面**的一个成分。
- **那个呼吸带 43%、主周期 2.60 秒，就是他的鼾声。** 它一直在那儿，
  只是「风扇单独也占这个带」把它淹了。

**所以做了一次「按响度分开量」**（逐帧按 RMS 排序，取最响的 1/4 与最静的 1/4 各算一遍）：

| 片段 | | 低频 | 质心 | 周期性 | 最强单音 |
| --- | --- | --- | --- | --- | --- |
| **鼾声 + 风扇** | 响 | **10%** | **955 Hz** | 0.30 | 0.12 |
| | 静 | 45% | 651 Hz | 0.20 | 0.09 |
| 唱歌 + 说话 | 响 | 38% | 386 Hz | **0.90** | **0.37** |
| | 静 | 53% | 620 Hz | 0.32 | 0.15 |

**两条结论：**

1. **「鼾声 + 风扇」里静的那一半（低频 45%、质心 651 Hz）就是纯风扇**（低沉的隆隆声）；
   响的那一半**变亮了**（低频 10%、质心 955 Hz）。**他的鼾声是叠在风扇上的、偏亮的成分。**
   这同时**订正了上面一条**：先前说「风扇呼吸带 45%」——那两段里还有敲桌子的声音，
   那个数不是纯风扇的。纯风扇该看这行「静」。
2. **他的鼾声是气声型（偏亮、宽带），不是教科书上那种低频软腭颤音。**
   这与他自己录的「假装鼾声」那一段完全对得上（低频 22%、质心 1186、周期性 0.13）
   ——**两个独立样本指向同一件事**。

**因此「鼾声 = 低频 + 周期性」这个模型对他根本不成立**：不是阈值没调对，是**模型选错了**。
所有频谱判据一条都过不了，是必然的。

（**唱歌那条误报不受这个订正影响，仍然成立**：任何由会呼吸的人发出的声音都有换气停顿，
那条通路必然误报。拆掉它是对的。）

**一个必须写下来的推论：那段被当作鼾声的录音，在每一个量上都是一台风扇的样子。**

| | 低频 | 质心 | 周期性 | 最强单音 | 呼吸带 | 包络节律性 |
| --- | --- | --- | --- | --- | --- | --- |
| 那段「鼾声」21.6s | 25% | 938 | 0.25 | 10% | 43% | 0.47 |
| 风扇 10.3s | 27% | 1144 | 0.29 | 12% | **45%** | 0.37 |
| 风扇 12.3s | 48% | 537 | **0.67** | **29%** | 31% | 0.31 |

**风扇的那一段比「鼾声」那一段更像鼾声**（低频 48% vs 25%、质心 537 vs 938、
周期性 0.67 vs 0.25）。这一条有两种解释，**目前分不出是哪一种**：

- 那段录音**确实是鼾声**，只是这个人的鼾声在频谱上就长这样（气声型），
  而那正好与风扇撞车；
- 或者那段录音**本身也不是鼾声**。

**两者指向同一个结论：现有这组特征不足以区分「鼾声」「风扇」与「人声」。**
使用方已被请去复核那段 21.6 秒的录音。

**据此新增 `spectralPeakShare`（最强单频占总能量的比例），并实测出它分得开：**

| 声音 | 最强单频占比（N=1024，12 段真机录音） |
| --- | --- |
| **哼歌**（`…995216978` 前段） | **37.2% / 44.3% / 48.9%** |
| 翻身吱呀（`…401600532` 5.7–7.2 s） | 34.5–38.8% |
| 拖椅子（`…1909283377032`） | 15.4–17.8% |
| 床品（`…812300532`） | 12.7–14.8% |
| 假装鼾声（`…011616978`） | 9.0–10.8% |

阈值 **0.30** 落在空档正中（离两边各约 1.2 倍）。**变异验证：把 `snoreMaxPeakShare` 抬到
1.0（等于取消这条判据），那段哼歌立刻回到「疑似打鼾」——已实测确认，不是推断。**

**为什么「人声」那一侧没有对称加上限**：翻身吱呀的 27–39% 与哼歌重叠，而**人声一个正样本
都没有**，没有可供落阈值的空档。照着单个样本卡阈值就是拟合，所以那一条作为**已知误报**
留在下面。

**仍不许用这 12 段调阈值**：正类各 1 个样本，调它就是往噪声上拟合。唯一按实测改过的是
`snorePitchStrength` 0.45 → 0.50，理由不是准确率（扫 0.4–0.7 都是 75%），而是**留余量**：
拖椅子那段量出来是 0.44，0.45 只比它高 0.01。`--sweep` 的完整读数：
`minEventMs` 500–4000、`snoreLowRatio` 0.30–0.60、`snoreCentroid` 400–1200 全部是
同一个数不动，`snoreMaxPeakShare` 0.20–0.40 也是——**说明准确率是被样本撑着的，
不是被阈值撑着的。**

**量出来的两条「旧判据是坏的」的证据（这是本轮改动的主要依据）：**

| 量什么 | 读数 |
| --- | --- |
| `syllableBandRatio` 在**完全没有调制**的信号上 | 白噪声 16.6%–29.7%，而阈值是 25% → **等于掷硬币** |
| `pitchStrength` 在同样两批信号上 | 12 段真实录音干净分成 **≤0.44** 与 **≥0.63** 两簇 |

| `spectralFlatness` 在真实音频上 | 好几段落在 **0.05–0.08**，恰好骑在旧阈值 0.05 上 |

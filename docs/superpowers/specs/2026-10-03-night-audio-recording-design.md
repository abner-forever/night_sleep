日期：2026-10-03
状态：待实现

## 问题

`SoundClips` 这张表从 schema v2 起就是按真实录音设计的，字段（`localUri` / `durationMs` /
`analysisStatus` / 被裁掉时置空 `localUri` 的语义）都在等一个真实的采集端；会话页那个
「鼾声/梦话记录」开关却只往 `AppSettings.soundRecordingEnabled` 写偏好，界面照实写着
「尚未接入录音，开关只保存偏好」（偏差 #7）。这一轮把中间那段补上。

**这一轮不做自动识别。** 不生成鼾声分类、不生成语音转写、不生成分析结论——项目没有、
也从未验证过任何分类模型（主规格 M3 第 3 条）。采集端只回答「这段时间有没有声响」，
「这是什么声音」一律由用户听过之后自己标。

## 一、实测：`record` 7.1.1 的真实能力

会话规格 §六 把切片路径列为「(a) 边录边分文件 / (b) 连续录临时文件后裁剪」，
并要求 **实测插件的真实能力后二选一**。实测（读 `record` 7.1.1 与 `record_ios` 2.1.1
的源码，非文档推断）结论如下。

| 事实 | 出处 |
| --- | --- |
| `AudioEncoder.pcm16bits` **流式**在 iOS 与 macOS 均可用 | `README.md` 的 Stream 矩阵 |
| 流式输出是**裸小端 PCM16，没有容器头**（逐帧拼字节，不写 WAV 头） | `record_ios/.../encoder/Pcm16BitsEncoder.swift` |
| 流式模式下**振幅与 PCM 出自同一条管线**，可同时取 | `record_ios/.../delegate/AudioStreamProcessor.swift` |
| 文件模式用 `AVAudioRecorder` 且 `isMeteringEnabled = true`，振幅也可用 | `record_ios/.../delegate/RecorderFileDelegate.swift` |
| iOS 侧自行 setCategory 为 `.playAndRecord` 并 activate，可用 `manageAudioSession` 让出 | `record_ios/.../extension/RecorderSessionExtension.swift` |
| 插件**不负责后台**；iOS 只需 `UIBackgroundModes: audio` 让会话保持激活 | `doc/bg_recording.md` |
| 依赖要求 Flutter ≥ 3.44 / Dart ≥ 3.12 | `record` 7.1.1 的 `pubspec.yaml`（本机 Flutter 3.47.5 / Dart 3.13.4，满足） |

**结论：走第三条路，不是 (a) 也不是 (b)。**

- (b) 按原措辞「连续录一个临时文件」峰值存储会爆：16kHz 单声道 16-bit = 32 KB/s，
  8 小时 **≈ 880 MB**，而且 AAC 想事后裁剪必须解码重编码（要引 ffmpeg）。
- 改成 PCM 流式之后，(b) 的两个缺点同时消失：**只有事件落盘**（一晚几十 MB），
  且边界由我们自己写文件决定，**不需要任何事后裁剪**——这正是 (a) 想要的低峰值存储，
  却没有 (a) 反复开关录音机带来的片段间隙与前置 padding 丢失。

新的第三条路：

```
PCM16 流 ──▶ RMS 每 100ms 一格 ──▶ 振幅序列 ──▶ segmentClips() ──▶ ClipRange
                     │                                              │
                     └──────────── 环形缓冲（前置 padding）──────────┘
                                                                    ▼
                                                          一段一个 WAV 文件
```

**代价（如实记下）**：整夜的 PCM 解码、RMS 计算与写盘都发生在 Dart 侧。iOS 在
`UIBackgroundModes: audio` + 激活的音频会话下不会挂起 App，Dart isolate 继续跑，
所以这条路成立；但真机整夜的后台存活**尚未验证**，见 §十二。

## 二、采集参数

```dart
RecordConfig(
  encoder: AudioEncoder.pcm16bits,
  sampleRate: 16000,
  numChannels: 1,
  autoGain: false,
  echoCancel: false,
  noiseSuppress: false,
)
```

- **16kHz 单声道**：鼾声与梦话的能量都在 8kHz 以内，16kHz 的奈奎斯特频率绰绰有余；
  再高只是白写盘。单声道因为话筒只有一个。
- **三个开关全部关掉**。`autoGain` / `echoCancel` / `noiseSuppress` 都会改变信号，
  开着就等于让「实测包络」变成对处理链的测量而不是对房间的测量——而包络是这一轮
  唯一对外宣称的测量结果。`noiseSuppress` 在 iOS 上本来也不支持。

## 三、切片：一条纯函数

会话规格 §六 已经定了形状，这里只补实现约束：

```
List<AmplitudeSample> ──segmentClips(ClipParams)──▶ List<ClipRange>
```

- 完全纯函数：不碰平台通道、不碰文件系统。**每一条边界都能单测**。
- 振幅序列由 PCM 每 **100ms** 聚合一格 RMS（`dBFS`）。聚合窗口固定，与插件吐出来的
  分片大小无关——否则同一段音频在不同设备上会切出不同的片段。
- `ClipParams` 的默认值（**全部未经验证**，必须真机实测后调）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 触发阈值 | −38 dBFS | 超过它算「有声」 |
| 结束阈值（滞回） | −45 dBFS | 低于它并持续一段时间才算结束 |
| 静音时长 | 2.0 s | 鼾声的换气停顿不会把一段切碎 |
| 前置 padding | 0.5 s | 起音不被切掉 |
| 最短片段 | 1.0 s | 短于此丢弃，挡掉整夜几百个碎片 |
| 最长片段 | 60 s | 超过强制切分 |
| 合并间隔 | 3.0 s | 相邻太近并成一段。**必须大于「静音时长 − 前置 padding」，否则这条规则永远触发不了**——短于静音时长的停顿本来就不会关掉那一段，合并窗口落在 `[静音时长, 静音时长 + 合并间隔 − 前置 padding]`。1.5 s 时这个窗口**恰好是空的**（2.0 − 0.5 = 1.5，判据又是严格小于），鼾声那 2–3 秒的换气停顿会被切成几十个碎片。取 3.0 s 后窗口是 2.0–3.5 秒 |

**阈值不是分类器。** 界面与文档一律称结果为「有声响的片段」，绝不叫「鼾声片段」。

`envelopeFor()` 是第二个纯函数：把片段区间内的振幅序列归一化并重采样成
`SoundClip.waveformBarCount`（38）条，作为该片段的**实测包络**——偏差 #2 到此终于
从一条限制变成一条「什么时候可以画」的规则，规则本身没变：**没有测量就不画**。

## 四、落盘：一条片段一个文件

会话规格 §六 已定：`SoundClips` **没有偏移量列**，所以一条片段必须对应一个独立文件。

- 格式：**WAV（PCM16 单声道 16kHz）**。插件的流是裸 PCM，WAV 头由我们自己写
  （44 字节，先写占位长度，关闭时 `setPosition` 回填）。
- 目录：`getApplicationSupportDirectory()/clips/`。**不用 `getTemporaryDirectory()`**
  ——那是「清除缓存」的地盘（偏差 #43），写进去会被用户清掉；也不用
  `getApplicationDocumentsDirectory()`，那在 iOS 上会进「文件」App 与 iCloud 备份。
- 文件名：`<clipId>.wav`。`clipId` 由片段起始时刻生成，带毫秒，天然有序。
- 前置 padding 由一个 **0.5 秒的环形缓冲**兜住：事件触发时先把缓冲里的 PCM 写进去，
  再继续写实时数据——这就是「片段不从中间开始」的实现。

## 五、被杀恢复：片段清单记在会话行里

`SoundClips.recordId` 是指向 `SleepRecords` 的外键，而记录行要等「结束睡眠」才写。
于是**片段在会话进行中无法入库**。

解法：`ActiveSessions` 加一列 `clipJournal`（text，可空）存一段 JSON 清单，
**每录完一段就更新一次**。生命周期与那一行会话完全重合：

```
结束会话：读会话行的清单 → 一个事务写（记录行 + 全部片段行）→ 删会话行（清单随之消失）
被杀重启：会话行还在 → 清单还在 → 用户照常「结束睡眠」，整晚录音保住
```

清单每项：`{id, startedAtUtc, durationMs, localUri, dbfsEnvelope}`。
存包络而不是原始振幅序列：包络只有 38 个数，原始序列一段就是几百个数。

**孤儿文件**：库是唯一真相来源。启动时扫 `clips/` 目录，文件名不在任何
`SoundClips.id` 里、也不在本会话清单里的，一律删掉。被杀之后重启、用户又把那次会话
丢弃了，那些文件就走这条路。

## 六、音频会话：白噪音优先，两者不重叠

会话规格 §六 已裁定，这里只记实现口径：**白噪音播放期间不录音**，
白噪音停止后（倒计时到点或用户停掉）录音才开始；开关为开不等于立刻开始录。

会话页据此显示三种真实状态，每一种都必须来自录音服务的实际状态，不是偏好值：

| 状态 | 界面 |
| --- | --- |
| 白噪音在播 | 「白噪音播放中 · 暂不录音」 |
| 正在录 | 「录音中」+ 醒目的录音指示 |
| 已停止（中断 / 失败） | 如实说明原因 |

**这段空档是一个真实的覆盖缺口，必须写在界面上**：白噪音最长 60 分钟，
那段时间里的鼾声或梦话不会被记录。

## 七、权限与平台配置

| 平台 | 改动 |
| --- | --- |
| iOS | `Info.plist`：`NSMicrophoneUsageDescription` + `UIBackgroundModes: [audio]` |
| macOS | `Info.plist`：`NSMicrophoneUsageDescription`；`DebugProfile.entitlements` 与 `Release.entitlements` 都加 `com.apple.security.device.audio-input` |
| Android | **已落地（v3.26，2026-10-14）**：平台目录 v3.11 生成，manifest 声明了 `FOREGROUND_SERVICE` 与 `FOREGROUND_SERVICE_MICROPHONE`；**v3.26 补上了服务本体** `NightRecordingService`（`foregroundServiceType="microphone"` + `NightAudioServiceHandler` + Dart 侧 `night_audio_service.dart`）——退到后台或锁屏后录音**在代码上**不再停。⚠️ **真机未验证**：服务是否真能挡住系统的端口静音（v3.19 实测的 `setRecordSilenced`），只有装到机器上跑一整夜才知道。`RECORD_AUDIO` **应用侧不声明**：实测 `record_android` 2.2.0 的 manifest 已自带并会在构建时合并（当初这一行写的「要补 RECORD_AUDIO」是没核过插件的推断，已订正）。详见 [安卓平台接入设计](2026-10-12-android-platform-design.md) §5.1 |

用途文案（本次由使用方确认）：

> 用于在夜间录制环境声音。录音片段仅保存在本机，不会上传；可在设置中随时删除，
> 超过保留期限的片段会自动清理。

**「去系统设置」不能复用通知那个入口。** `reminders.dart` 的 `openSystemSettings()`
跳的是通知设置页；麦克风要另找一个通用的应用设置页跳转，不能复用它然后声称能跳到
麦克风权限。

权限被拒时与通知完全一致：**开关回弹、不写入偏好、给「去系统设置」入口**。

## 八、数据模型：schema v5 → v6

只加三列可空列，**不重建任何表**。

| 表 | 新列 | 用途 |
| --- | --- | --- |
| `ActiveSessions` | `clipJournal` text，可空 | 进行中会话的片段清单（§五） |
| `SoundClips` | `waveformEnvelope` text，可空 | 实测包络，JSON 数组，38 个数 |
| `SoundClips` | `labeledAtUtc` dateTime，可空 | 用户是否已经标过这一段 |

`labeledAtUtc` 这一列是**对会话规格 §二「录音不需要改表」的一处订正**。那条说
「未标注 vs 杂音」的区别放在显示层做，但显示层没有可依据的事实：用户手动标成
「杂音」与从未标注都写 `kind = 'noise'`，两者在库里一模一样。要么砍掉「杂音」这个
标注选项，要么补一列——补一列更诚实，也保住了规格 §六 明写的三个标注选项。

`waveformEnvelope` 同理必须落库而不是读取时解码：片段被保留期限裁掉之后
`localUri` 为空，但**形状仍然是真的**，卡片理应继续画得出波形却拒绝回放
（`SoundCard` 早就写好了这个分支）。

## 九、标注：只由用户来做

- 详情页的声音卡列出片段：时刻、时长、标注状态。
- 点开可**真实回放**（`localUri` 为空时显示「这段录音未保留在本地，无法回放」——
  这句话与那个分支都已经在位）。
- 可标注为**打鼾 / 梦话 / 杂音**，写回 `kind` 并把 `labeledAtUtc` 置为当前时刻。
- **未经标注的片段一律显示为「待标注」**，不是「杂音」。
- `transcript` / `analysis` 留空，`analysisStatus` 为 `pending`。

**现有 `SoundCard` 的播放按钮是假的**——`_togglePlayback` 只改 `_playing` 这个
局部布尔，不产生任何声音。这一轮要把它接上真的 `just_audio` 播放器，
否则「可回放」又是一句没兑现的话。

**演示数据必须补 `labeledAtUtc`**：演示片段的 kind 是示例数据本身的一部分，
不补的话整套演示数据会全部显示成「待标注」。

## 十、保留期限与删除

- 默认保留**最近 7 晚**（本次由使用方确认）。清理时：删音频文件、把 `localUri` **置空**、
  **`SoundClips` 行保留**——这正是表注释早就写好的语义，详情页会如实显示
  「这段录音未保留在本地」，而不是片段凭空消失。
- **只清理 `source = 'recording'` 的行**；演示片段随演示数据一起清。
- 设置页给出**当前占用**与「删除全部录音」入口。占用读不到就如实说读不到，
  不显示一个编出来的 `0 B`（与偏差 #43 的「清除缓存」同一条规则）。
- 「清除缓存」**不碰录音**（它只动 `getTemporaryDirectory()`）；「删除全部本地数据」
  会一并清掉录音与片段文件。
- **删一条记录也要带走它的音频（v3.20 补的实现）。** 此前 `SleepRepository.delete(id)`
  只删行，`sound_clips` 靠外键级联跟着没，**磁盘上的 WAV 一行代码都不碰**——真机实测：
  9 条片段行全没了、**9 个 WAV 一个不少地留在盘上**，而那个确认框写的是「声音事件都会被
  永久删除，此操作无法撤销」（[验证记录](../../verification-log.md) v3.19）。文件要等到
  **下一次冷启动**的孤儿清理才被扫掉。

  现在两条路径都走 `clip_pruning.dart` 里那两个同时握着库与文件仓库的函数：
  `deleteRecordWithRecordings()` 与 `deleteAllUserDataWithRecordings()`。
  **`SleepRepository` 上不再有 `delete(id)` / `deleteAllUserData()`**——那个仓库只有
  `AppDatabase`，留一个只删行的入口就是给同一个洞留下一次机会。

  **两处顺序都是刻意的**：文件路径必须在删行**之前**读（`record_id` 是带 cascade 的外键，
  行一没就再也问不出 `localUri`）；删全部数据那条还多收一类东西——**当前会话清单里那些
  已经落盘、还没入库的片段**，会话行一删清单就跟着消失，不在这里一起删，它们就正好落进
  「谁也不认识」的缝里。删文件失败会被 `ClipFileStore.deleteClip` 吞掉，留下的是一个孤儿
  （下次冷启动清掉），而不是一行指着不存在文件的记录。

## 十一、界面

- **会话页顶部**：醒目的「录音中」指示，取自录音服务的真实状态（§六 那张表）。
- **会话页鼾声行**：副标题由「尚未接入录音，开关只保存偏好」改为真实状态描述。
  **偏差 #7 到此作废**，主规格 §8 的那一行要改写为「已实现，见偏差 #27」，
  而不是留在表里继续描述一个已经不存在的限制。
- **详情页空状态**：现在的「全程安静，无异常声音」有一个具体的毛病——它把
  「跑过检测、结论是没有」与「根本没录」说成了同一件事。使用方在 iPad 上就是这样
  被误导的：他以为录音开着，界面却像检测完了似的下了一个「安静」的结论。

  改成一个**在两种情形下都为真**的说法：「**这一晚没有声音片段**」，
  副句写明它可能是安静、也可能是没有录音。

  **为什么不做「没录到声响 / 根本没录音」的两分法**：那需要一个「那一晚录音到底
  有没有跑起来」的事实，而这个事实现在没有被存下来——它既不在 `SleepRecords`、
  也不在片段行里（没录到就是零行，零行不带任何信息）。为此再加一列，代价与它买到
  的那点区分度不成比例。等真机上跑过几晚、确认这个区分确实常被用到，再补不迟。
  在那之前，界面的义务是**不下那个它没资格下的结论**，这一点已经做到了。
- **设置页 · 声音检测**：保留开关，副标题改写为真实能力；新增占用与「删除全部录音」。

## 十二、未验证与真机验收

以下每一条都是**必须在真机上跑过才算数**的，不能靠单测或构建通过顶替：

1. **整夜后台存活**：锁屏后 Dart isolate 是否持续收到 PCM、片段是否持续落盘。
   这是整条路的**前提**——录不到整夜，功能等于不存在。
   **2026-10-14 真机验证（v3.19）：存活这一半成立，但它没带来能用的录音。** 一整晚
   （01:22:49 → 08:30:21）采集端只起过一次、字节时钟全程跟着真实时间走，说明 isolate
   确实活着、PCM 确实在流；**可那 7 小时的数据是逐样本全零**——平台静音了录音端口。
   根因、三次对照读数与判据见 [`docs/verification-log.md`](../../verification-log.md)
   v3.19 与本文 §十四。
2. **阈值的实际表现**：§三 那组默认值全部是拍的。要用真实打鼾 / 梦话样本调
   `ClipParams`，并确认安静房间不会因为底噪触发、鼾声不会被换气停顿切碎。
3. **与白噪音的切换**：白噪音倒计时到点之后录音是否真的接上。
4. **中断**：来电 / 其他应用抢麦克风时，已录片段保留、界面如实显示已停止。
5. **耗电**：整夜流式处理的电量代价。若不可接受，退回「文件模式 + 事后裁剪」
   （代价是峰值存储 880MB）。

## 十四、平台静音：把「录不到」如实说出来（2026-10-14 新增）

### 问题（真机实测，不是推测）

[验证记录 v3.19](../../verification-log.md) 把使用方自己开的那一整晚会话拉下来离线复算，
结论是：**录音链路本身自洽，但那 7 小时里平台交给应用的是逐样本全零。**

- 08:30 那条片段的前 3 格（300 ms）**1600 个采样无一非零**，第 4 格起才是有底噪的真实音频；
- `dumpsys media.audio_flinger` 里那条轨道的 `Client` 就是本应用的 pid、`Port Id = 135`，
  日志 `setRecordSilenced(general), portId:135, appType:0, silenced 1` **静音的正是我们的
  端口**；同一端口三次读数：前台 `Sil = n` → 灭屏 100 s 后 **`Sil = s`** → 唤醒 8 s 后回到
  `n`；
- 而 `cmd appops get … RECORD_AUDIO` **全程是 `allow … (running)`**，`record` 插件也从不报
  任何中断。

于是**应用手里拿到的状态就是「正在录」**，界面照着它写了整夜「录音中」。这不是应用撒谎，
是平台骗过了它——但用户看到的仍然是假话，与偏差 #7 / #31 是同一类失败。

### 裁定

1. **判据是「逐样本全零」，不是「很安静」。** 真实麦克风永远有本底噪声（这台机器上这间房
   实测约 −55 dBFS）。一整格 1600 个采样全是 0，只可能是平台没把麦克风交给应用。
   1 LSB 的底噪（`amplitude: 1`）**不算**——安静与「没有麦克风」是两件事，代码里是
   `_analyseWindow` 返回的两个字段（`dbfs` / `allZero`），测试里各有一条。
   **不能用「dBFS 等于 −160」代替它**：那是个有下限的近似值，稍高于它的安静房间会被压到
   同一个读数上。
2. **新增 `NightRecordingState.silenced`，不复用 `stopped`。** 流还活着、采样还在源源不断
   地来，麦克风随时可能回来（实测：应用一回到前台就自动恢复）。这时说「已停止」是假的，
   说「录音中」也是假的——它既不响，也没停。
3. **不在这条路上停录。** 主动停下来才是真的把后面可能回来的声音丢掉。
4. **界面照实说，那颗灯不亮。** 会话页那一行写 `kSilencedMicReason`；「录音中」那颗小灯
   只认 `recording`，于是自动不亮。
5. **`kSilentMicRun = 60 秒`，与 §三 那七个参数一样是拍的，待真机标定。** 给得宽是因为
   起录瞬间的空缓冲够不到它；实测 Android 上从灭屏到端口静音是几十秒级，触发得不算晚。

### 这条**不**解决什么（不许写成解决）

- **它只是把假话改成真话，不让整夜录音变成能录。** 真正让 Android 上录得下来的东西是
  前台服务（`FOREGROUND_SERVICE_MICROPHONE`）。本节写于 v3.20，当时那件事**还没做**
  （清单里只有声明，`dumpsys activity services` 是空的）。**v3.26 补上了服务本体**
  （`NightRecordingService`，见 [安卓平台接入设计](2026-10-12-android-platform-design.md) §5.1），
  但**它挡不挡得住那次静音真机未验证**，而本节这条状态（`silenced`）本身就是那次静音的兜底
  说辞——**阈值与状态都不修那个根因**，服务也还没被证明修好了它。
- **也没把「这一夜麦克风是死的」写进记录。** 第二天打开那条睡眠记录，看到的仍然是
  「0 条声音事件」，与「一夜真的没出声」长得一模一样。要区分它们得给 `sleep_records`
  加一列（或另存一段录音覆盖情况），那是 schema v8 的事，不在本轮（**v7 已被 v3.26 的 `sound_clips.auto_analysis` 用掉**，见[片段自动分析设计](2026-10-14-night-clip-auto-analysis-design.md) §四）。

### 回归方法

- `test/night_recorder_test.dart` 的「平台静音」一组（5 条）：阈值前不翻 / 越过就翻 /
  声音回来回到 `recording` / 1 LSB 底噪不算 / 全零必须连续 / 停录后不再停在 `silenced`。
- `test/sleep_session_page_test.dart` 两条：`recording` 时那一行写「录音中」且**灯亮**；
  `silenced` 时写 `kSilencedMicReason`、**不许出现「录音中」**、**灯不亮**。后者按颜色
  （`NightStyle.liveDot`）找那颗灯，改颜色就变红。
